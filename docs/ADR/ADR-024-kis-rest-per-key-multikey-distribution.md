# ADR-024: KIS REST Rate Limit per-key 확인 및 배치/백필 멀티키 분산

- **상태**: 승인 (SPEC-COLLECTOR-BATCH-001 국내 배치 수집 구현으로 확정 — 2026-06-11)
- **일자**: 2026-06-10
- **관련**: ADR-023(rate limiting 구현 방법), SPEC-COLLECTOR-TOKEN-001(REST 단일키 제한)

---

## 맥락

ADR-023은 KIS REST에 Bucket4j로 TPS 20 제한을 적용하기로 했으나, 그 한도가 **앱키별(per-key)로 독립 적용되는지, 고객/IP 단위로 통합(aggregate) 적용되는지** 명시하지 않았다. 이 구분은 1-7(REST 배치 수집) 설계를 가른다:

- **per-key이면** 5개 앱키로 분산 시 처리량이 ~5배 → 배치·백필을 빠르게 수집.
- **통합이면** 분산해도 처리량은 동일 → 단일키로 설계.

또한 SPEC-COLLECTOR-TOKEN-001이 collector의 모든 REST 호출을 `isa` **단일 앱키**(`KisApiExecutor.firstCredential()`)로 제한했으므로, per-key 이점을 쓰려면 별도의 멀티키 실행 경로가 필요하다. 1-7 백필은 종목 × 과거기간이 커서 처리량이 임계 변수다.

공식 문서·커뮤니티 어디에도 REST 적용 단위가 명시돼 있지 않아(WebSocket만 앱키 단위로 확인됨), 실측으로 판별했다.

---

## 결정

1. **실측으로 per-key(앱키별) 확인.** 일회용 프로브로 동일 read 엔드포인트(`search-stock-info`)를 단일키 vs 5키 라운드로빈으로 점증 부하한 결과, 5키가 단일키의 약 5배 처리량으로 선형 확장했고 에러가 집계가 아닌 **키당 부하**에 비례했다. 통합 가설은 기각된다.

2. **고용량 배치/백필 REST는 5개 앱키로 분산**한다(멀티키 실행 경로). 저용량·단발 호출은 SPEC-COLLECTOR-TOKEN-001대로 `isa` 단일키를 유지한다 — 하이브리드.

3. **운영 목표는 보수적으로 키당 ~15 TPS(마진 포함), 집계 ~75 TPS**로 잡는다. 키당 rate limiter는 ADR-023의 Bucket4j 패턴을 키별로 인스턴스화한다.

---

## 검토한 대안

### 대안 A — 단일키 유지 (TOKEN-001 그대로)

| 항목 | 내용 |
|------|------|
| 구현 | 가장 단순(현행 `KisApiExecutor` 그대로) |
| 처리량 | 단일키 한계(~20 TPS ballpark)에 묶임 |
| 백필 | 종목·기간이 커 수집 장기화 |

기각. per-key 이점을 버려 배치/백필 처리량이 불필요하게 제약된다.

### 대안 B — 전 REST 5키 분산

| 항목 | 내용 |
|------|------|
| 처리량 | 최대(집계 ~75–100 TPS) |
| 설계 영향 | TOKEN-001의 "REST=isa 단일키" 결정을 전면 번복 |
| 부담 | 5개 access_token 상시 발급·관리 재도입 |

기각. 단발·저용량 호출까지 멀티키로 돌릴 이득이 없고, TOKEN-001 취지(불필요한 다계좌 토큰 발급 제거)를 훼손한다.

### 대안 C — 하이브리드 (채택)

| 항목 | 내용 |
|------|------|
| 배치/백필 | 5키 분산(per-key 이점 확보) |
| 단발·저용량 | `isa` 단일키 유지(TOKEN-001 보존) |
| 토큰 | 멀티키 경로 진입 시점에 해당 키 access_token을 Lazy 발급(기존 `getValidToken(alias)` 활용) |

채택. per-key 처리량 이점과 TOKEN-001 취지를 동시에 만족한다.

## 근거 데이터 (프로브 실측, 2026-06-10)

| 구분 | 단일 키 | 5키 집계 |
|------|---------|----------|
| 성공 TPS(최대) | ~21–23 | ~94–113 |
| 키당 ~10 부하 시 에러율 | (단일 7.4% @ 목표10) | 1.2% @ 목표50 |
| 결론 | per-key — 5키가 ~5배 확장, 에러는 키당 부하에 비례 |

**한계·주의 (과대해석 금지)**:
- **절대 한도값은 이 프로브로 정밀 확정 불가**(8초 창·요청별 계측 없음). "~20/키"는 측정·문서가 부합하는 ballpark이며, 프로브가 확실히 답한 것은 **per-key 여부**뿐이다.
- **저부하 에러엔 비-소진성 성분 포함**: 목표 5 TPS(초당 ~5건)는 한도 20 초과가 불가능한데도 EGW00201이 1건 발생 → 클라이언트 한도초과로 설명되지 않는 KIS 측 간헐 거부가 존재한다. 에러를 전부 한도초과로 해석하면 안 된다.
- **프로덕션의 `capacity 2 / refill 8`(~8 TPS)은 측정값이 아니라 임의 보수 설정**이며 실한도 근거로 쓰지 않는다.

## EGW00201 에러 처리 (2026-06-10 NAS 로그 확인)

**도착 형태**: EGW00201은 **HTTP 500**으로 도착한다. 바디는 `{"rt_cd":"1","msg_cd":"EGW00201","msg1":"초당 거래건수를 초과하였습니다."}`. 500이므로 `RestClient.retrieve().body()`가 역직렬화 전에 예외를 던져 `KisApiResponse.validateRtCd()`/`KisApiBusinessException` 경로를 타지 않고 `RestClientException`(RestClientResponseException 500)으로 분류된다.

**현재 처리의 문제**:
- `KisStockInfoClient.fetchStockInfo`는 `@Retryable`이 없어 EGW00201 시 **재시도 없이 종목을 skip**한다. 실측: 15:45 동기화 회차에서 다수 종목이 EGW00201로 누락(로그 43건).
- `KisWatchlistClient`의 `@Retryable(retryFor=RestClientException)`은 재시도하나, `WatchlistSyncService`가 `KisRateLimiter.consume()`을 1회만 호출한 뒤 그 안에서 재시도하므로 **재시도가 rate limiter를 우회**한다(추가 토큰 미소비) → retry storm 소지.
- EGW00201을 일반 500과 동일하게 취급 — rate-limit 전용 처리 없음.

**1-7 요구사항**:
- 500 바디의 `msg_cd == "EGW00201"`을 식별해 **rate-limit 전용(일시적·재시도 가능)** 으로 분류하고, 영구 비즈니스 오류(인증·잘못된 파라미터)와 구분한다.
- 재시도는 반드시 **rate limiter를 재경유(토큰 재획득)** 하여 retry storm을 방지한다.
- 배치/백필은 완전성이 필요하므로 EGW00201에 **드롭 금지** — backoff 후 재시도로 누락을 방지한다.

## 결과 및 후속

- 1-7(REST 배치 수집/백필) 착수 시 **키별 `KisRateLimiter` + 멀티키 실행 경로**(라운드로빈 또는 키 파티셔닝)를 구현하고 본 ADR을 "승인"으로 전환한다.
- 키당 rate limiter 페이싱은 ADR-023의 Bucket4j(refillGreedy) 패턴을 따른다. 비-소진성 간헐 거부에 대비해 배치 경로는 거부 시 재시도(backoff)를 둔다.
- WebSocket의 per-key(세션/구독) 제약은 별개이며 ADR-003이 관할한다.
- **정밀 지속 한도가 필요하면** 부드럽게 페이싱한 단일키를 분(分) 단위로 돌리며 초별 성공/거부를 로깅하는 추가 측정이 필요하다(본 ADR 범위 외).
